# 第 10 章:常見問題 FAQ

> 整理新手第一次接觸 CI/CD 時,最常見的疑問。

---

**Q1:CI/CD 一定要用 GitHub Actions 嗎?**

不一定。CI/CD 是一個**概念**,GitHub Actions 只是實現這個概念的其中一種工具。
市場上還有其他常見的 CI/CD 工具,例如 GitLab CI、Jenkins、CircleCI、Travis CI 等等。
它們的核心邏輯都很類似(觸發事件 → 執行一連串自動化步驟 → 回報結果),
只是設定檔的語法跟細節有差異。學會 GitHub Actions 的觀念後,要換用其他工具會容易上手很多。

---

**Q2:我沒有錢租伺服器,也可以練習 CD(自動部署)嗎?**

可以。本專案示範的 GitHub Pages 就是完全免費的方案,很適合拿來練習靜態網站的自動部署。
如果之後想練習部署「動態」的應用程式(例如需要資料庫的網站),
也有一些平台提供免費或低成本的方案可以練習,但這已經超出本教學的範圍了。

---

**Q3:為什麼我的 workflow 沒有被觸發?**

最常見的原因有:

1. `.yml` 檔案沒有放在正確的路徑:必須是 `.github/workflows/檔名.yml`,資料夾名稱跟大小寫都要完全正確。
2. YAML 縮排錯誤,導致整份設定檔格式不正確(可以參考 [第 5 章](./05-GitHubActions入門.md) 的格式說明)。
3. `on:` 底下設定的觸發條件跟你實際的操作不符,例如設定了 `paths` 限制,但你改動的檔案不在那個路徑底下。
4. 分支名稱寫錯,例如設定的是 `branches: ["main"]`,但你推送到的其實是別的分支。

排查的第一步,建議先到 repo 的 Actions 分頁看看有沒有任何執行紀錄,如果完全沒有紀錄,
通常代表觸發條件沒有被滿足;如果有紀錄但顯示失敗,再點進去看詳細的錯誤訊息。

---

**Q4:測試在我自己的電腦上可以跑,但在 CI 裡卻失敗,為什麼?**

這是很常見的狀況,通常代表你的電腦環境跟 CI 提供的虛擬機器環境不完全一樣。可能的原因包括:

- 電腦上安裝的程式語言版本,跟 workflow 裡設定的版本不同。
- 電腦上有一些「順手裝的工具或設定」,但這些東西沒有被記錄在專案裡,所以 CI 環境沒有。
- 檔案路徑的大小寫問題(某些作業系統對大小寫不敏感,但 Linux 通常是敏感的,而 CI 常用的
  `ubuntu-latest` 就是 Linux 系統)。

養成習慣:盡量讓專案裡的設定檔(例如 `package.json` 裡指定的版本)跟 CI 使用的環境保持一致。

---

**Q5:什麼是 Badge(徽章)?我在很多專案的 README 上都看過。**

Badge 是放在 README 最上方,一個小小的圖示,通常用來顯示這個專案「目前 CI 檢查的狀態」
(例如顯示「通過」或「失敗」)。它的原理是引用 GitHub 提供的一個動態圖片網址,
這個網址會即時反映最新的 workflow 執行結果。這只是一個方便團隊快速掌握專案健康狀態的小工具,
不影響 CI/CD 本身的運作邏輯。

---

**Q6:CI/CD 是不是就等於「自動化測試」?**

不完全相同,但關係很密切。**自動化測試是 CI 流程裡經常包含的其中一個步驟**,
但 CI/CD 整體涵蓋的範圍更廣,包含建置、測試、打包、部署等一整套流程
(可以回顧 [第 3、4 章](./03-持續整合CI.md) 的完整說明)。
自動化測試是讓 CI/CD 真正發揮效果的重要基礎,但兩者不是同一件事。

---

**Q7:如果我的專案很小、只有我自己一個人開發,還需要 CI/CD 嗎?**

即使是個人專案,CI/CD 依然有價值:

- 你自己也會犯錯,自動化檢查可以在你自己都沒發現的時候,提早攔截問題。
- 未來如果有其他人想一起參與這個專案,已經設定好的 CI/CD 可以確保大家的貢獻都經過一致的檢查標準。
- 這是很好的練習機會,讓你熟悉業界實際在用的工作流程,對未來求職或參與其他專案都有幫助。

---

**Q8:接下來我還可以學什麼?**

如果你已經理解了本教學的內容,可以嘗試:

- 幫本專案的計算機範例([`examples/calculator`](../examples/calculator))新增更多功能(例如次方運算),
  並且自己寫對應的測試。
- 修改 [`examples/website`](../examples/website) 的內容或版面設計,推送後觀察自動部署的過程。
- 研究看看,如果要把測試涵蓋率(有多少比例的程式碼被測試覆蓋到)也顯示在 CI 結果裡,該怎麼設定。
- 嘗試在 GitHub 的 repo 設定裡,開啟分支保護規則,體驗「CI 沒過就不能合併」的實際效果。

---

## 結語

CI/CD 表面上看起來是一堆設定檔跟工具的組合,但它背後真正的精神,
其實跟 [第 1 章](./01-什麼是CICD.md) 一開始講的手搖飲料店比喻一樣簡單:

> **把重複、容易出錯的檢查與上架流程,交給一套穩定、一致的自動化機制去完成,
> 讓人可以把心力專注在真正需要判斷力的事情上。**

希望這份教學,能幫助你建立起對 CI/CD 清楚且扎實的理解。歡迎回到 [README](../README.md) 複習整體架構。
