# 第 9 章:最佳實踐與常見錯誤

> 這一章整理業界實際導入 CI/CD 時,常見的建議做法,以及新手容易踩到的錯誤。

---

## 9.1 好的做法

### (1) 小步快跑,頻繁提交

一次 commit 只做一件小事,一次 Pull Request 也不要包山包海。原因在 [第 3 章](./03-持續整合CI.md)
已經解釋過:改動越小,出問題時越容易定位,審查程式碼的人也更容易看懂。

### (2) 測試要涵蓋正常情況,也要涵蓋異常情況

延續 [第 7 章](./07-在CI中測試.md) 的除法範例:不要只測「能算出正確答案」的情況,
也要想清楚「輸入奇怪的值時,程式會怎麼反應」。常見要考慮的異常情況包括:

- 空值、負數、超出範圍的數字。
- 空字串、格式不正確的文字。
- 網路請求失敗、外部服務沒有回應。

### (3) 讓 CI 執行得又快又聚焦

如果每次推送都要等 20 分鐘才知道結果,大家會漸漸失去耐心、甚至養成「先跳過檢查」的壞習慣。
本專案在 [`ci.yml`](../.github/workflows/ci.yml) 裡使用了 `paths` 設定,
讓 workflow 只在相關檔案改動時才執行,這是讓 CI 保持精簡高效的常見手法。

### (4) 把敏感資訊放進 Secrets,不要寫死在程式碼裡

如果 workflow 需要用到密碼、API 金鑰等敏感資訊,GitHub 提供了 **Secrets** 功能
(在 repo 的 Settings → Secrets and variables 裡設定),讓你可以在 workflow 裡安全地引用這些值,
而不會被公開寫在程式碼或設定檔裡讓任何人看到。

```yaml
      - name: 使用機密資訊的範例
        run: deploy-tool --token ${{ secrets.MY_DEPLOY_TOKEN }}
```

### (5) 明確設定權限,遵循最小權限原則

就像 [第 8 章](./08-自動部署到GitHubPages.md) 提到的 `permissions` 設定,
一個 workflow 只應該擁有它真正需要用到的權限,不多不少。這樣即使設定檔或某個相依套件出了問題,
影響範圍也會被限制在最小範圍內。

### (6) 保護重要分支

可以在 GitHub 的 repo 設定裡,針對 `main` 這類重要分支開啟「分支保護規則」,
例如規定「CI 檢查沒有通過,就不允許合併 Pull Request」。這樣可以確保 `main` 分支
永遠維持在「已經通過自動化檢查」的狀態,不會有人不小心把壞掉的程式碼直接合併進去。

## 9.2 常見錯誤

### 錯誤一:測試寫得太少,或只測試「快樂路徑」

只測試一切順利的情況,測試通過率 100%,看起來很安心,
但實際上使用者遇到的問題往往發生在你沒有測試到的「邊界情況」。

**建議**:寫測試時,養成習慣問自己「如果輸入的是奇怪的值,會發生什麼事?」

### 錯誤二:把 CI 檢查失敗當作噪音,習慣性忽略或強制合併

如果團隊裡的人習慣看到 CI 失敗就直接忽略、或用管理員權限強制合併,
CI/CD 這套安全網就名存實亡了。

**建議**:把 CI 失敗當成「必須先處理的事」,而不是可有可無的參考資訊。

### 錯誤三:一個 workflow 做太多事,難以維護

把「測試」、「打包」、「部署」、「發通知」全部塞進同一個巨大的 workflow 檔案,
一旦某個步驟改壞了,很難快速定位問題,而且每次小改動都要跑完整套流程,浪費時間。

**建議**:依照職責拆分成多個 workflow(就像本專案把 `ci.yml` 跟 `deploy.yml` 分開一樣),
各自負責單一、明確的目的。

### 錯誤四:把敏感資訊直接寫在程式碼或設定檔裡

例如把資料庫密碼、API 金鑰直接寫在 `.yml` 檔案裡,一旦這個 repo 是公開的,
任何人都能看到這些機密資訊,可能造成資安問題。

**建議**:一律使用 GitHub Secrets 或其他機密管理工具,絕對不要把機密資訊直接寫進程式碼裡。

### 錯誤五:過度依賴持續部署,卻沒有配套的回復機制

如果採用 [第 4 章](./04-持續交付與持續部署CD.md) 提到的「持續部署」,
一定要同時考慮:如果部署出去的版本有問題,要怎麼快速回復到前一個正常版本?

**建議**:確保部署流程本身是可以快速重複執行的(例如重新部署前一個 commit),
或是額外設計自動化的回復(rollback)機制。

---

## 9.3 小結

| 面向 | 建議做法 |
|------|----------|
| 提交習慣 | 小步快跑,頻繁提交 |
| 測試 | 涵蓋正常與異常情況 |
| 執行效率 | 只在相關檔案改動時觸發 |
| 機密管理 | 一律使用 Secrets,不寫死在程式碼裡 |
| 權限設計 | 遵循最小權限原則 |
| 分支管理 | 對重要分支開啟保護規則 |
